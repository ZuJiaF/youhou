# 靠日志定位问题，不靠猜

## 核心原则

**当用户表达代码有问题或有 Bug 时，AI 不要靠猜测、也不要只靠自己阅读/搜索代码来定位问题。第一步永远是：先在可疑的运行路径上插入调试代码（`console.log` 等），让用户运行后把日志反馈回来，用真实的运行数据定位问题。**

阅读代码只能形成"假设"，日志才能给出"事实"。用事实定位问题，比用假设猜测准确得多。

## 为什么

- 静态阅读代码容易漏掉：实际传入的参数值、真实的分支走向、异步时序、外部数据的真实结构、环境差异
- 猜测式修改往往"改了一处、错了另一处"，反复试错浪费时间
- 日志把"我以为的运行路径"变成"真实的运行路径"，一眼看出偏差在哪

## 工作流程

### 1. 先形成怀疑范围（可以读代码，但只用来选埋点位置）

快速判断问题可能出在哪几条运行路径上，确定要在哪些关键节点埋点。

### 2. 插入调试代码，追踪可疑路径

在可疑路径的关键节点插入调试日志，覆盖：
- 关键函数的**入口和出口**（确认是否被执行、执行顺序）
- 关键**变量/参数的实际值**（确认数据是否符合预期）
- **分支判断点**（确认走了哪个分支）
- **异步/回调的时序**（确认执行先后）
- **外部数据**（接口返回、数据库查询结果）的真实结构

日志要带清晰的标签和**写入日期**，便于用户回传后快速对应，也便于未来追溯调试历史：

```javascript
console.log('[debug][2026-07-09][函数名] 入参:', JSON.stringify(参数))
console.log('[debug][2026-07-09][函数名] 走到了分支 A，此时 x =', x)
```

**日期格式**：`YYYY-MM-DD`，使用插入调试代码当天的日期。日期的作用：
- 标记这段调试代码是什么时候写的
- 未来阅读时可按日期分组理解调试历史
- AI 可据日期判断调试代码的新旧和关联性

### 3. 请用户运行并回传日志

明确告诉用户：
- 需要执行什么操作来触发这段代码
- 把控制台/日志里带 `[debug]` 标记的输出复制回来

### 4. 根据日志定位

对比日志与预期，找出偏差点：值不对？分支走错？根本没执行？时序颠倒？

### 5. 不够就再加一波，往复迭代

如果一波日志还不足以定位（例如缩小到某个范围但还不够精确），**在已有日志的基础上继续加更细的调试代码**，再让用户运行反馈，如此往复，逐步逼近根因。

### 6. 定位后再修复，注释保留调试代码

- 确认根因后再动手改，避免盲目修改
- 修复验证通过后，**将调试代码注释掉，而非删除**

#### 为什么保留（注释）而不删除

1. **历史线索**：未来 AI 读到注释的调试代码，能推测这段代码过去出过什么问题、排查过什么路径
2. **快速复用**：同一区域再出 Bug 时，AI 可直接取消注释重新激活，不用重新思考埋点位置
3. **日期分类**：通过 `[debug][日期]` 标签，可按时间线理解代码的调试历史和问题演变

#### 注释格式

```javascript
// [debug-done][2026-07-09] 以下调试代码已完成使命，保留供未来参考
// console.log('[debug][2026-07-09][函数名] 入参:', JSON.stringify(参数))
// console.log('[debug][2026-07-09][函数名] 走到了分支 A，此时 x =', x)
```

- 在注释块顶部加一行 `[debug-done][日期]` 标记，说明该组调试代码已完成
- 如果调试代码超过 5 行，可在顶部注释中简述当时排查的问题：
  ```javascript
  // [debug-done][2026-07-09] 排查：用户登录后 token 未正确写入 storage
  // console.log('[debug][2026-07-09][login] token =', token)
  // ...
  ```

#### 重新激活

当同一区域再次出现问题时，AI 应：
1. 先检查附近是否有已注释的调试代码
2. 如果有且埋点位置仍相关 → 取消注释直接激活（把日期更新为当天）
3. 如果埋点位置已不适用（代码结构变了）→ 重新插入新的调试代码

## 例外情况

以下情况可以不先埋日志：
- 一眼可见的明显错误（拼写错误、语法错误、明显的类型不匹配）
- 编译器/linter/报错栈已经精确指向了具体行和原因
- 用户已经提供了足够的日志或错误信息

## AI 助手工作规范

1. **用户报 Bug 时**：第一反应是"我先加几行调试日志，你运行后把输出发我"，而不是直接猜原因或直接改代码
2. **埋点要精准**：只在可疑路径埋点，日志带 `[debug][日期][函数名]` 格式
3. **日期必须写**：每条调试日志都要带当天日期，格式 `YYYY-MM-DD`
4. **告诉用户怎么触发**：说明要做什么操作、把哪些日志回传
5. **迭代式定位**：一波不够就基于已有日志再加一波，往复逼近
6. **定位后注释保留**：修复完成后将调试代码注释（不是删除），加 `[debug-done]` 标记
7. **复用已有调试代码**：插入新调试代码前，先检查附近有没有可激活的历史调试代码

## 涉及后端时的配合

如果调试代码加在 uniCloud 云对象/云函数里，插入日志后需按 [[unicloud-deployment-reminder]] 提醒用户重新部署，否则日志不会生效。
