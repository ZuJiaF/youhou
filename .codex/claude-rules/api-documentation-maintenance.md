# 接口文档维护规范

## 核心原则

**在开发过程中，当用户提供接口信息（请求体、响应体、网络请求流水）时，主动维护项目的接口文档，避免重复测试和信息丢失。**

适用于：
- 第三方 API 集成项目
- 逆向工程项目
- API 客户端开发
- 微服务对接
- 爬虫项目

## 文档维护时机

当用户提供以下信息时，需要维护接口文档：
- ✅ 接口请求体示例
- ✅ 接口响应体示例
- ✅ 网络请求流水（Network 面板截图/日志）
- ✅ 接口参数说明
- ✅ 状态码、枚举值等
- ✅ 接口认证信息（Token、签名等）

## 工作流程

### 1. 查找对应接口文档

在项目中查找是否已有该接口的记录文件：
- 按 URL 路径匹配
- 按接口功能匹配
- 检查项目的接口文档目录

### 2. 有记录则查漏补缺

对比用户提供的数据与已有文档：
- ✅ 补充缺失的字段
- ✅ 更新变化的值
- ✅ 添加新发现的状态枚举
- ✅ 记录不同场景下的响应差异
- ✅ 更新字段说明

### 3. 无记录则新建

创建新的接口文档文件，包含：
- 接口 URL
- 请求方法（GET/POST/PUT/DELETE 等）
- 请求头（Headers）
- 请求体结构及关键字段说明
- 响应体结构及关键字段说明
- 重要的枚举值（如状态码、state 字段的可能值等）
- 认证方式（如需要）
- 备注和注意事项

## 文档组织方式

### 方式 1：按子项目文件夹组织

```
项目根目录/
├── 子项目A/
│   ├── api-docs/
│   │   ├── user-login.md
│   │   ├── get-product-list.md
│   │   └── update-order.md
│   └── src/
├── 子项目B/
│   ├── api-docs/
│   │   └── payment.md
│   └── src/
```

### 方式 2：集中式文档目录

```
项目根目录/
├── docs/
│   └── api/
│       ├── 目标网站A/
│       │   ├── auth.md
│       │   └── products.md
│       └── 目标网站B/
│           └── orders.md
├── src/
```

### 方式 3：单文件汇总

```
项目根目录/
├── API.md          # 所有接口集中在一个文件
└── src/
```

项目在 CLAUDE.md 中指定使用哪种方式。

## 接口文档模板

### 标准模板

```markdown
# 接口名称

## 基本信息

- **URL**: `https://api.example.com/v1/users/login`
- **方法**: POST
- **说明**: 用户登录接口

## 请求

### 请求头

```json
{
  "Content-Type": "application/json",
  "User-Agent": "Mozilla/5.0..."
}
```

### 请求体

```json
{
  "username": "user123",
  "password": "pass123",
  "remember": true
}
```

### 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| username | string | 是 | 用户名 |
| password | string | 是 | 密码 |
| remember | boolean | 否 | 是否记住登录，默认 false |

## 响应

### 成功响应（200）

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "userId": "12345",
    "token": "eyJhbGc...",
    "expireAt": 1698765432000
  }
}
```

### 失败响应（200）

```json
{
  "code": 1001,
  "message": "用户名或密码错误",
  "data": null
}
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| code | number | 状态码，0 为成功，非 0 为失败 |
| message | string | 提示信息 |
| data.userId | string | 用户 ID |
| data.token | string | 认证 Token |
| data.expireAt | number | Token 过期时间戳（毫秒） |

### 状态码枚举

| code | 说明 |
|------|------|
| 0 | 成功 |
| 1001 | 用户名或密码错误 |
| 1002 | 账号已被禁用 |
| 1003 | 登录过于频繁 |

## 备注

- Token 有效期为 7 天
- 同一账号最多同时 3 个设备登录
- 登录失败 5 次后账号锁定 30 分钟
```

## AI 助手工作规范

### 1. 主动识别接口信息

当用户提供接口相关信息时，主动询问：
```
我注意到你提供了 xxx 接口的信息，是否需要我记录到接口文档中？
```

### 2. 查找现有文档

```
我先检查一下项目中是否已有该接口的文档...
[读取 api-docs/ 目录]
```

### 3. 更新或创建

- 如果已存在：`已找到该接口文档，我将补充新的字段信息...`
- 如果不存在：`未找到该接口文档，我将创建新文档...`

### 4. 确认完成

```
接口文档已更新：docs/api/user-login.md
新增字段：remember、expireAt
更新状态码：1003（登录过于频繁）
```

## 示例对话

```
用户：[提供网络请求截图]
这是登录接口的请求和响应

AI：我注意到这是 /v1/users/login 接口的信息，让我检查是否已有文档...
[检查] 未找到该接口文档，我将创建新文档。

[创建] docs/api/user-login.md
已记录：
- 请求方法：POST
- 请求字段：username, password, remember
- 响应字段：userId, token, expireAt
- 状态码：0（成功）、1001（用户名或密码错误）

后续调用该接口时可以参考此文档。
```

## 注意事项

- 敏感信息（真实 Token、密码）不要写入文档，使用占位符
- 记录接口的多种响应场景（成功、失败、边界情况）
- 定期检查接口文档是否过期，API 变更时及时更新
- 枚举值尽可能完整，避免遗漏
